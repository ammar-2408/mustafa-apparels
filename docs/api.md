# API

The apps talk to the server in two ways:
- **Server Actions** for form mutations from our own UI (sign-up excluded — Better Auth owns that).
- **Route Handlers** (`app/api/**/route.ts`) for auth, uploads, search suggestions, cross-app revalidation and machine-readable files.

## 1. Conventions

**Every server action / route handler follows this order:**
1. Authenticate/authorize first: `await requireUser()` or `await requireAdmin()` from `packages/auth`. A public action has no check here. Guards throw; route handlers map that to 401/403, and server actions map it to an `ActionResult` with `UNAUTHENTICATED` or `FORBIDDEN`.
2. Parse and validate input with a Zod schema from `packages/validators` (`safeParse`; reject unknown keys with `.strict()`).
3. Rate-limit if listed below.
4. Call `packages/core` — no business logic in the route file.
5. Revalidate caches / write audit log.
6. Return a typed result.

Guards and core throw `CoreError` (`packages/core/errors.ts`), with codes `NOT_FOUND`, `CONFLICT`, `VALIDATION`, `UNAUTHENTICATED`, `FORBIDDEN` and `RATE_LIMITED`. `toActionError()` in `packages/core/action-result.ts` turns one into an `ActionResult` with its safe message, and anything else into `INTERNAL` with a generic message, so SQL or stack details never reach the browser. `UNAVAILABLE` means a service the action needs isn't configured here (auth on a mock preview with no database).

**Result type for server actions**
```ts
type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: ErrorCode; message: string; fieldErrors?: Record<string, string[]> } };

type ErrorCode = 'VALIDATION' | 'UNAUTHENTICATED' | 'FORBIDDEN' | 'NOT_FOUND'
               | 'CONFLICT' | 'RATE_LIMITED' | 'INTERNAL' | 'UNAVAILABLE';
```
Messages are safe to show users; never include stack traces, SQL or whether an email exists.

**Route handler errors** use the same shape as JSON with matching HTTP status (400, 401, 403, 404, 409, 429, 500).

## 2. Storefront (`apps/web`)

| `submitInquiry` | `{ productId?, name (2–80), email, phone (PK format, optional if email), message (≤2000), website (honeypot, must be empty) }` | none (user linked if logged in with a verified email) | 5 / 10 min / IP | `{ inquiryId }` |

### Page data (Server Components, via `core`)
`getHomeData()`, `listProducts({ category?, page, sort, filters })`, `getProductBySlug(slug)`, `resolveSlugRedirect(entity, slug)`, `searchProducts({ q, page, filters })`, `getSiteSettings()`, `getWishlist(userId)`, `listMyInquiries(userId)`.

`filters`: `{ pieces?, dressCategories?, fabric?, design?, season?, outfitStyle?, colorFamily?, priceMin?, priceMax? }` (`productFilters` in `packages/validators/search.ts`). Each filter except price takes a list: a suit matches any value within one filter, and every filter that is set. Allowed values: `docs/catalog.md` §4. There is no size filter. `listProducts` also returns which values exist among published suits, so the UI hides empty options.

As built (`core.products`, step 2.11): `list(db, input, { scope })` returns `{ items, total, page, pageCount, facets }`, 24 cards a page (`PAGE_SIZE`), with `pageCount` at least 1 and a page past the end returning no items. The public scope shows published, undeleted suits in visible collections; the admin scope shows every undeleted suit. An unknown or hidden collection slug throws `NOT_FOUND`. `facets` lists the values the collection's published suits have (not narrowed by the current filters), plus the price bands in use. `priceMax` is inclusive. Status changes only through `setStatus` (step 2.12): `create` accepts only drafts and `update` refuses `status`. `update` re-checks the price, colour and compare-at rules on the stored suit merged with the change. `duplicate` names the copy "… (copy)" with the first free slug of `<slug>-copy`, `-copy-2`, and so on. `restore` brings an archived suit back as a draft. `/search` and admin pass `filters` to the server. `/shop` and collection pages never do: they filter and sort `/api/suits` in the browser (ADR-018).

### Listing URLs (ADR-017)

| URL | Shows | Canonical |
|---|---|---|
| `/shop`, `/collections/[slug]` | Page 1 | Itself |
| `/shop/page/[n]`, `/collections/[slug]/page/[n]` | Page `n`, for `n` ≥ 2 | Itself |
| `/shop/page/1`, `/collections/[slug]/page/1` | 301 to the page without `/page/1`, set in `next.config` with `statusCode: 301` | — |

- `n` comes from the route param, never from `searchParams`, and is validated with Zod. It must be a whole number from 2 up with no leading zeros. `/page/0`, `/page/abc`, `/page/01` and anything past the last page call `notFound()`.
- Pages are statically generated with `generateStaticParams` and tagged. A page that appears after the build is generated on first request and then cached. `revalidateTag` also clears a cached 404 once that page comes into range.
- An old collection slug redirects permanently, including on its `/page/[n]` URLs. Redirects made while rendering use `permanentRedirect()`, which sends 308; search engines treat it like a 301.
- No `loading.tsx` above these routes: once streaming starts, a 404 or redirect loses its real status code.

## 3. Admin (`apps/admin`)

All actions call `requireAdmin()` first (role `admin` + 2FA-verified session). Build each with `adminAction(schema, handler)` from `apps/admin/lib/action.ts`: it runs the guard, then the schema, then the handler, and returns an `ActionResult`. The loop test in `apps/admin/test/admin-actions-authz.test.ts` picks up every `app/**/actions.ts` export automatically. The one exception is `startTwoFactorSetup`, which allows only an admin who hasn't turned 2FA on yet, and is in the loop too. All mutations write `audit_log` and trigger storefront revalidation. The loop also fails on a `'use server'` file not named `actions.ts`, and checks that a banned admin and an admin without 2FA get `FORBIDDEN` (the setup action excepted).

**Admin rate limits** (`apps/admin/lib/limits.ts`, `enforceLimit(limit, userId)`, keyed by the admin's user id; throws `RATE_LIMITED`):

| Limit | Max | Fail mode | Used by |
|---|---|---|---|
| `admin-2fa-setup` | 5 / min | closed (a password check Better Auth doesn't see) | `startTwoFactorSetup` |
| `admin-write` | 60 / min | open | every admin mutation (built into `adminAction`, after validation, so a bad form never counts) |
| `upload-sign` | 30 / min | open | `/api/upload/sign` |

The suit media actions also call `revalidatePath('/suits/<id>')`, so the admin page's fresh data comes back with the action's answer, with no separate `router.refresh()`.

Media saves (`addProductMedia`, `setVideoPoster`) call `verifyAsset` (`packages/core/integrations/media.ts`) before writing: it reads the asset back from Cloudinary and refuses, with every reason at once, anything outside this suit's `products/<id>/` prefix, the format list, 10 MB / 50 MB, 60 s or over 1 hour old. A refused upload made for this suit is deleted from Cloudinary; an id pointing at another suit's file is refused but never deleted. The row stores Cloudinary's width, height, bytes, format and duration (`core.media.add`). Schemas: `mediaAddInput`, `mediaReorderInput`, `mediaPrimaryInput`, `mediaPosterInput`, `mediaAltInput`, `mediaDeleteInput` in `packages/validators/media.ts`.
| `createCategory` / `updateCategory` / `reorderCategories` / `setCategoryActive` (`app/(panel)/collections/actions.ts`) | `categoryInput` / `categoryUpdateInput` / `categoryReorderInput` (every id) / `categoryVisibilityInput` `{ id, isActive }` | `categories`, `products`, `category:<slug>` (old and new slug on a rename); reorder: `categories` only |
| `setInquiryStatus` | `{ id, status }` | — |
| `updateSiteSettings` | `{ key, value }` (validated per key) | `settings` |

## 4. `POST /api/revalidate` contract

```http
POST {WEB_URL}/api/revalidate
Content-Type: application/json
X-Timestamp: 1730000000
X-Signature: hex(hmac_sha256(REVALIDATE_SECRET, timestamp + "." + body))

{ "tags": ["products", "product:abc123", "category:dhanak"] }
```
- Reject if signature invalid (constant-time compare), timestamp older than 5 minutes, body > 2 KB, or tags not matching `^(products|categories|settings|product:[\w-]+|category:[\w-]+)$`.
- Responses: `200 { revalidated: [...] }`, `401` (signature or time), `400` (body over 2 KB, not JSON, or a tag outside the list; 1–20 tags), `503` when the storefront has no `REVALIDATE_SECRET` (it never runs unsigned). All `Cache-Control: no-store`. POST only.
- Code: `signRevalidate`, `verifyRevalidate` and `createRevalidator` in `packages/core/integrations/revalidate.ts`; tag schema `revalidateBody` in `packages/validators/revalidate.ts`; route `apps/web/app/api/revalidate/route.ts`; admin caller `revalidateStorefront(tags)` in `apps/admin/lib/revalidate.ts`, the last step of every mutation.
- The storefront calls `revalidateTag(tag, { expire: 0 })`, so the next visitor after a save gets the change (not one more stale view, as `'max'` would give).
- The caller never throws: a network failure, timeout (5 s) or error answer is logged (no secret) and the save still succeeds. In `INTEGRATIONS_MODE=mock`, or without `WEB_URL` / `REVALIDATE_SECRET`, it logs and skips.

## 5. Validation schemas (examples)

### 5.1 Product

```ts
// packages/validators/product.ts
const pieceDetail = z.object({
  piece: z.enum(['shirt', 'dupatta', 'trouser']),
  fabric: z.string().trim().min(1).max(40).optional(),
  finish: z.string().trim().max(40).optional(),
  length_m: z.number().positive().max(10).optional(),
}).strict();

export const productInput = z.object({
  name: noBannedTerms(z.string().trim().min(2).max(120)),
  slug: noBannedTerms(z.string().regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/).max(140)),
  designCode: z.string().trim().regex(/^[A-Za-z0-9-]{1,20}$/).nullable(),
  description: noBannedTerms(z.string().max(5000)).default(''),
  price: z.number().int().min(0).max(10_000_000).nullable(),
  compareAtPrice: z.number().int().positive().nullable(),
  categoryId: z.string().min(1),
  pieces: z.enum(['two_piece', 'three_piece']),
  pieceDetails: z.array(pieceDetail).max(3),
  collectionType: z.string().trim().max(40).nullable(),
  dressCategories: z.array(z.enum(DRESS_CATEGORIES)).max(6),
  fabric: z.enum(FABRICS),
  design: z.array(z.enum(DESIGNS)).max(9),
  season: z.enum(['winter', 'summer', 'all_season']).nullable(),
  outfitStyle: z.enum(OUTFIT_STYLES).nullable(),
  mainColor: noBannedTerms(z.string().trim().max(30)).nullable(),
  colorFamily: z.enum(COLOR_FAMILIES).nullable(),
  accentColors: z.array(z.string().trim().min(1).max(30)).max(12),
  motifs: z.array(noBannedTerms(z.string().trim().min(1).max(60))).max(12),
  relatedDesignCodes: z.array(z.string().regex(/^[A-Za-z0-9-]{1,20}$/)).max(10),
  careInstructions: noBannedTerms(z.string().max(1000)).default(''),
  availability: z.enum(['in_stock', 'low_stock', 'out_of_stock']),
  status: z.enum(['draft', 'published', 'archived']),
  featured: z.boolean(),
  attributes: z.record(z.string(), z.unknown()).default({}),
  seoTitle: noBannedTerms(z.string().max(70)).optional(),
  seoDescription: noBannedTerms(z.string().max(160)).optional(),
}).strict()
  .refine(p => p.status !== 'published' || p.price !== null, {
    path: ['price'], message: 'Add a price before publishing',
  })
  .refine(p => p.status !== 'published' || (p.mainColor !== null && p.colorFamily !== null), {
    path: ['colorFamily'], message: 'Add a colour before publishing',
  })
  .refine(p => p.compareAtPrice == null || (p.price !== null && p.compareAtPrice > p.price), {
    path: ['compareAtPrice'], message: 'Must be higher than price',
  });
```

`DRESS_CATEGORIES`, `FABRICS`, `DESIGNS`, `OUTFIT_STYLES` and `COLOR_FAMILIES` live in `packages/validators/taxonomy.ts` and match `docs/catalog.md` §4 (a test reads the doc's table).

As built (step 2.9), `packages/validators/product.ts` also exports:
- `productUpdateInput`: `id` plus only the fields that change, with no defaults. Zod 4 applies a `.default()` even inside `.partial()`, which would reset fields an update never sent, so update schemas never carry defaults.
- `productRuleErrors(row)`: the cross-field rules (price and colour before publishing, compare-at above price). `productInput` runs them; `core` runs them again on the stored row merged with an update.
- `productStatusInput` (`{ id, status }`) and `productListInput` (`{ categorySlug?, page, sort: newest | price_asc | price_desc, filters }`).
- `pieceDetails` lists each piece once, with at most 2 on a 2-piece suit.

The other modules are `category.ts` (`categoryInput`, `categoryUpdateInput`, `categoryReorderInput`), `inquiry.ts` (a phone or an email is required; blank form fields count as not given), `search.ts` (`searchInput`, `suggestInput`, `productFilters`; the query has control characters removed and spaces collapsed, then 2–60 characters), `settings.ts` (`settingInput`, one schema per key) and `phone.ts` (`pkMobile`: a Pakistani mobile in any common format, stored as E.164).

### 5.2 Media

| Kind | Formats | Max size | Other limit |
|---|---|---|---|
| `image` | JPEG, PNG, WebP | 10 MB | Alt text required |
| `video` | MP4, MOV, WebM | 50 MB | Max 60 seconds; alt text required |

Limits are checked in the browser for quick feedback, then **enforced on save** from Cloudinary's metadata. An upload over the limit is deleted and the save returns `VALIDATION`.

```ts
// packages/validators/media.ts
export const mediaInput = z.object({
  kind: z.enum(['image', 'video']),
  publicId: z.string().startsWith('products/').max(200),
  url: z.string().url(),
  alt: noBannedTerms(z.string().trim().min(3).max(200)),
  posterPublicId: z.string().startsWith('products/').max(200).nullable(),
  sortOrder: z.number().int().min(0),
  isPrimary: z.boolean(),
}).strict()
  .refine(m => !m.isPrimary || m.kind === 'image', {
    path: ['isPrimary'], message: 'The main item must be a photo',
  });
```
Width, height, bytes, format and duration are read from Cloudinary on the server, never accepted from the client.

## 6. Versioning

Internal APIs (server actions) change with the code. If a public JSON API is ever added (e.g. for a mobile app), put it under `/api/v1/` with OpenAPI docs in this file.
